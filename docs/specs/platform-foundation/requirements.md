# Platform Foundation 需求

## 1. 定位

Platform Foundation 负责招生 CRM 的组织、成员、角色权限、数据范围、导航模块配置和用户自助账号能力。业务模块必须建立在这一层之上，不各自实现成员、角色或可见范围。

## 2. 组织架构

- 每个租户必须且只能有一个根部门；根部门不可删除，也不能把普通部门提升为第二根。
- 同一父部门下名称唯一，移动部门时必须防止形成环。
- 部门树返回直属成员数量、负责人等当前管理页所需信息。
- 删除部门只允许在现有安全规则满足时执行，不能留下孤儿成员或破坏唯一根。
- 企业 Provider 组织同步必须落到当前租户组织树，并受目标承载节点、映射和冲突规则约束。

## 3. 成员与角色

- 一个成员可以关联多个角色，数据库以 `UserRole` 多对多为事实源。
- 功能权限是所有角色权限码并集；`*` 表示全部权限。
- 成员创建/编辑至少关联一个有效角色；角色删除不得造成成员失去全部角色。
- 系统角色不可删除，角色成员关系可以由成员页或角色成员页维护。

## 4. DataScope

数据范围必须按“当前动作权限”计算，而不是简单取用户所有角色中最大的范围。

- 仅拥有目标权限或 `*` 的角色参与该权限的数据范围合并。
- `ALL` 直接覆盖为全部。
- `SELF` 只允许本人负责的数据。
- `DEPT` 为本部门。
- `DEPT_AND_CHILD` 为本部门及下级部门。
- `CUSTOM` 为配置部门及其下级部门。
- 多角色范围取并集，但无关权限角色不得扩大目标动作范围。

列表读取、详情、更新、删除和统计都必须传入明确权限码；业务 Service 不得绕开统一 DataScope。

## 5. 模块与导航配置

- 模块配置以 `tenantId + key` 持久化启用状态和排序。
- 当前主导航产品边界只允许 `home / lead / customer / system`。
- 当前顶部导航只允许 `task / event / notify / about / help`。
- 历史数据库中的退出 key 可以保留记录，但 API 不得继续暴露或让前端重新配置出无效入口。
- `system` 等固定模块不可被错误关闭；尚无真实页面/能力的模块不得进入可配置定义。
- 模块开关只控制发现入口，不能替代后端权限 Guard。

## 6. 个人中心与 API Key

- 当前用户可读取个人资料、角色、部门、语言等上下文，并更新允许自助修改的手机号/邮箱。
- 修改密码必须校验原密码并递增 `authVersion`，使旧 access/refresh 会话失效。
- 个人 API Key 使用 `X-Access-Key / X-Secret-Key`，按用户所有权、启用状态、有效期和权限验证。
- API Key 认证成功后仍进入同一 RBAC/DataScope，不获得额外业务权限。
- Secret 只在创建时返回必要值，不以明文持久化或日志输出。

## 7. 安全与验收

- 所有平台查询首先按 tenant 隔离。
- 权限目录、角色授权上限、成员状态和 DataScope 必须由服务端执行。
- 组织/角色/成员写操作进入操作日志。
- 平台基础改动必须覆盖角色组合、权限撤销、跨租户、唯一根、模块历史 key 过滤和 API Key 会话路径。
