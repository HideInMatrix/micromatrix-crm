# Pool Recycle 需求

> **实现状态：核心功能已实现。** 截至 2026-11-09，线索池与客户公海的 2 分钟真实回收闭环均已通过本地 PostgreSQL、Redis、BullMQ 和独立 Worker 验证，覆盖领取后从未跟进、领取后新增跟进并重新计时两种场景。PC/H5 页面视觉验收，以及 Redis/Worker 故障恢复和并发边界专项测试仍待完成。2 分钟仅为本地测试阈值，不是生产默认值。

## 1. 定位

线索池与客户公海的自动回收是一项按资源时间条件触发的业务能力。管理员配置动态时间后，系统应在对应时间阈值到达后尽快检查并回收，不应要求用户等待每天固定时刻的批量扫描。

本领域覆盖线索池和客户公海；不改变现有池成员范围、领取限制、客户跟进完结判断、负责人历史、回收原因和通知语义。

## 2. 动态时间语义

- 动态时间必须以所选业务时间字段的实际时间为锚点，而不是以每天扫描时刻或用户打开配置页面的时刻为锚点。
- 例如在测试环境选择「最近领取时间 + 超过 2 分钟」，领取时间为 10:00:00，则最早在 10:02:00 到期。2 分钟是验证延迟调度能力的测试阈值，不是生产默认值；生产阈值由管理员按招生业务配置。任务调度延迟只影响实际执行时刻，不改变到期计算；正常运行时应以到期后数秒内触发为目标，不承诺毫秒级准时。
- 选择「最后跟进时间 + 超过 24 小时」时，每次新增跟进都会更新锚点并重新计算到期时间；旧任务不得依据旧跟进时间回收资源。
- `storageTime` 可按配置选择创建时间（Created）、最近领取时间（Picked）或二者；二者同时选择时，必须都满足阈值。
- `followUpTime` 优先以资源当前 `followTime` 为锚点；如果从未产生跟进记录（`followTime` 为空），则回退到最近一次领取时间 `collectionTime`。因此仅配置最后跟进时间动态阈值时，从未跟进的线索/客户也会从领取时刻开始计时。两种时间都缺失时不创建计划，也不命中回收条件。
- AND / OR 的现有组合语义必须保留。延迟任务只是触发重新评估的机制，不能替代 `ResourceRecycleConditionEvaluator` 的最终判断。
- 动态阈值至少支持分钟、小时、天、周；保留现有 `CUSTOM,<amount>,BEFORE_HOUR/DAY/WEEK/MONTH` 等已保存格式的兼容解析。分钟采用向后兼容的新单位标识，例如 `CUSTOM,2,BEFORE_MINUTE`。
- 固定时间范围及 TODAY、LAST_SEVEN 等区间型动态条件继续按现有语义判断；不能将区间条件错误转换为单一的延迟时长。

## 3. 触发与重新调度

以下业务事件发生并提交成功后，必须刷新该资源的回收计划：

- 线索或客户从池中被领取，`collectionTime` 更新。
- 创建、分配、转移负责人等操作使资源开始由成员负责并设置领取时间。
- 新增跟进使 `followTime` 更新；当规则引用最后跟进时间时，重新计算到期时间。
- 线索或客户进入池、转换客户、删除、负责人清空等导致资源不再符合回收对象条件时，取消或使旧计划失效。
- 池启用/停用、自动回收开关或回收规则发生变化时，相关资源的计划必须重新计算；关闭自动回收或停用池后不得继续执行旧计划。

同一资源在任一时刻只能有一个有效的回收计划。重新领取、跟进、转移负责人或修改规则后，旧任务即使仍从队列中触发，也必须识别为过期任务并安全退出。

## 4. 执行前置校验

每次延迟任务触发时，必须从 PostgreSQL 重新读取当前资源和池配置，并重新执行全部业务判断：

- 租户、资源类型、资源 ID 和目标池匹配。
- 资源仍由有效负责人持有，且不在池中。
- 线索尚未转化为客户；客户仍符合当前客户业务状态。
- 目标池仍启用，自动回收仍开启，当前规则仍有效。
- 当前创建/领取/跟进时间与任务预期锚点一致。
- 当前时间条件仍由现有 evaluator 判定为满足。
- 客户仍未命中管理员配置的跟进完结规则；完结字段配置失效时，继续遵循暂停客户自动回收的安全策略。

并发跟进、重新领取、负责人转移和自动回收时，必须通过事务锁及带预期负责人/时间戳的条件更新（CAS）保证只有一个业务动作成功。旧任务、重复任务和重试不得重复写入负责人历史、回收日志或通知。

## 5. 可靠性与恢复

- PostgreSQL 是回收计划及业务状态的事实源；Redis/BullMQ 只承担延迟投递和执行传输，不得成为唯一任务记录。
- 业务时间变更与回收计划更新应使用同一数据库事务或可靠 Outbox，避免数据库已提交但任务计划永久丢失。
- Worker 启动时从 PostgreSQL 恢复尚未完成且在 Redis 中缺失的计划；`PoolRecycleTask` 的 `PENDING` 状态承担持久化待派发记录，Worker Dispatcher 每 5 秒派发并对失败记录退避重试。当前不运行独立的低频 Redis Job reconciliation，也不执行每分钟全量资源扫描。
- BullMQ job 至少一次投递；业务执行必须幂等。瞬时错误有限重试并退避；资源状态已变化属于安全 no-op，不应无限重试。
- 任务延迟或 Redis 不可用时，计划必须保留在 PostgreSQL，服务恢复后能够继续执行；不得因为队列不可用而丢失回收意图。
- 线索和客户任务必须按租户隔离；Worker 不能信任队列 payload 中的租户、负责人或池规则快照。

## 6. 用户可配置性

- 动态时间配置应提供明确的数值和单位选择，至少覆盖分钟、小时、天、周；保留现有 24/48/72/168 小时快捷选项。
- 不要求管理员手工输入 `CUSTOM,2,BEFORE_MINUTE` 等内部序列化字符串。
- 配置说明应明确时间从所选字段的时间点开始计算，而不是从每天扫描时间开始计算。
- 2 分钟只作为本地/测试环境的短时验收阈值，不作为生产默认值；生产环境的回收时长由管理员根据业务需要配置。

## 7. 验收标准

- [已通过] 线索池与客户公海「最后跟进时间」配置 2 分钟：领取后从未跟进时，使用最近领取时间作为初始锚点；真实领取后由 BullMQ 延迟任务触发 Worker，资源回到原池、负责人和领取时间清空，任务进入 `COMPLETED`。
- [已通过] 线索池与客户公海领取后新增跟进：真实写入跟进记录并执行 `FollowUpsService.touchTarget` 事务逻辑，`generation` 递增、`expectedFollowTime` 与 `dueAt` 更新；旧领取任务不回收，新的跟进时间超过 2 分钟后才回收。
- [已通过] 2026-11-09 本地真实数据验收：4 条记录（线索/客户各 2 条）全部完成回收；2 条无跟进记录按领取时间回收，2 条有跟进记录按最后跟进时间重新计时后回收；4 条任务均无 `lastError`，跟进记录和负责人历史保留。
- [待专项验收] 重新领取或转移负责人：旧任务不得影响新的负责人和新领取周期。
- [待专项验收] 关闭自动回收、停用池、手动移入池、线索转客户或客户跟进完结：旧任务触发时不得错误回收。
- [已通过单元测试] `followUpTime` 有跟进记录时以最后跟进时间计时；无跟进记录时回退到领取时间；领取时间也缺失时不创建计划、不命中条件。该计算器由线索池和客户公海共用；两类资源的真实端到端闭环仍分别验收。
- [部分验证] AND / OR、多时间字段和固定时间条件保持既有语义；Evaluator 单元测试通过，全部组合仍需专项集成覆盖。
- [待专项验收] Worker 重启、Redis 重启、队列重复投递、任务失败重试后，回收结果仍正确且仅发生一次。
- [已通过后端闭环] 客户公海真实 PostgreSQL + Redis + BullMQ + Worker 闭环，覆盖无跟进和新增跟进重新计时；PC 页面视觉和 H5 业务操作仍待专项验收。
