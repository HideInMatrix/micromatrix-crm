# W3.2 企业微信组织同步需求

## 1. 目标

在 W3.1 已完成企微配置、凭据加密和连接测试的基础上，实现企业微信部门与成员的可审计同步闭环。同步必须以 CordysCRM 源码为业务基线，同时保护 MicroMatrix 已存在的负责人、审批、角色数据范围和其他业务引用。

## 2. Cordys 源码事实

- `UserSyncController` 使用独立 `SYS_ORGANIZATION:SYNC` 权限，提供启动同步和查询同步中状态两个接口。
- `ThirdDepartmentService` 使用租户级锁异步执行，读取已验证且开启 `startEnable` 的第三方配置，依次获取 token、部门和部门成员。
- `WeComDepartmentService` 使用 `/department/list` 和 `/user/list`，部门以企微 ID 建树；成员按主部门过滤，并保存企微 `userid`。
- 首次同步中，`DataHandleUtils.handleAddData` 会清理原成员和部门后整体重建，并关闭原消息渠道配置。
- 后续同步按第三方 `resourceId/resourceUserId` 更新或新增；企微不存在的系统成员会被禁用，缺失部门不会显式删除。
- 配置的 corpId 变化会把首次同步标识重置；成功同步会写操作日志、清理缓存并通知操作人。
- Cordys 页面在组织架构“更多”中提供平台同步；未配置、未验证、未开启或正在同步时不可执行，并对首次/后续同步展示不同风险提示。

## 3. 建议的 MicroMatrix 适配

Cordys 的首次删除策略与当前 Prisma 外键和业务负责人关系不兼容。W3.2 建议采用“预览后应用”的受控同步：

- 预览阶段只拉取和计算差异，不修改部门、成员或业务数据。
- 已有外部映射优先匹配；无映射但与本地邮箱/手机号/同级部门名称碰撞时标记冲突，不自动合并。
- 应用时只新增或更新已确认的企微资源；本地手工资源不因首次同步被删除或禁用。
- 后续同步只禁用已建立企微映射、但本次企微快照中已不存在的成员；部门保留映射失效状态，不物理删除。
- 冲突必须由管理员选择“绑定现有资源”或“跳过”，不得通过名称猜测覆盖本地记录。

这是相对 Cordys 的有意安全增强，不改变企微数据获取、外部 ID 匹配、成员缺失禁用、权限和状态门控等核心规则。

## 4. 用户故事

### US1：同步前检查

作为组织管理员，我希望先看到企微部门和成员与本地数据的差异，以便在修改组织架构前确认影响。

### US2：冲突处理

作为组织管理员，我希望明确处理邮箱、手机号或部门名称冲突，以免同步误合并已有成员或部门。

### US3：可追溯执行

作为系统管理员，我希望看到每次同步的状态、统计、失败原因和逐项结果，以便定位问题和安全重试。

### US4：外部资源持续更新

作为组织管理员，我希望后续同步更新已映射资源，并禁用企微中已离职的映射成员，同时不影响本地手工成员。

## 5. 验收需求

### R1：配置和权限门槛

1. 当管理员开启组织同步时，系统必须要求企微配置已保存且最近一次连接测试成功。
2. 当用户启动预览、应用同步或读取批次详情时，系统必须校验独立的 `system:dept:sync` 权限。
3. 当企微 corpId、agentId 或 Secret 变化时，系统必须关闭同步并使未应用的预览批次失效。
4. 当同步未开启、配置未验证或 Secret 不可解密时，系统必须拒绝创建预览并返回明确错误。

### R2：企微快照与预览

1. 当用户创建同步预览时，系统必须按 Cordys 顺序获取 token、全部可见部门和各部门成员。
2. 当企微接口返回错误、超时、空部门列表或重复外部 ID 时，系统必须把批次标记为失败且不修改本地组织数据。
3. 当快照获取成功时，系统必须规范化主部门、成员负责人标识、名称、邮箱、手机号和职位，并生成部门/成员差异项。
4. 预览结果必须统计新增、更新、禁用、不变、冲突和跳过数量，并允许分页查看逐项差异。
5. 预览必须保存当次规范化快照；应用阶段不得重新拉取并悄悄改变用户已确认的内容。
6. 当应用可见范围只包含一个子部门及其后代、未返回企业全局根部门时，系统必须把唯一可见子树顶点规范化为同步根部门；多个互不相连的可见子树仍必须拒绝。

### R3：外部映射与冲突

1. 当同一租户、平台和外部部门 ID 已有映射时，系统必须使用该本地部门，不得按名称重新匹配。
2. 当同一租户、平台和外部用户 ID 已有映射时，系统必须使用该本地成员，不得按邮箱或手机号重新匹配。
3. 当无映射的部门与同一父部门下本地部门同名时，系统必须生成冲突项。
4. 当无映射的成员与本租户成员邮箱或手机号碰撞时，系统必须生成冲突项。
5. 当用户提交冲突解决方案时，系统必须验证绑定目标属于当前租户且尚未绑定到另一个同平台外部资源。
6. 未解决的冲突必须阻止整批应用；标记为跳过的项目不得产生或修改映射。

### R4：部门应用规则

1. 当应用新增部门时，系统必须按父子顺序创建并保存企微外部 ID 映射。
2. 当应用已映射部门时，系统必须同步名称、父部门和排序，并保持部门树无环。
3. 企微全局根部门或唯一可见子树顶点必须新增或更新到创建预览时指定的本地目标部门之下；目标部门本身的名称、排序和上级关系不得被同步修改。
4. 当已映射部门本次不再出现时，系统必须把映射标记为失效并保留本地部门，不得物理删除部门或破坏角色数据范围。

### R5：成员应用规则

1. 当应用新增企微成员时，系统必须创建本地成员、外部身份映射和默认角色关系；本地密码必须为不可预测随机值。
2. 当企微未返回可用邮箱时，系统必须按 Cordys `sys_user.email` 语义保存 `NULL`；同步成员默认关闭普通密码登录。
3. 当应用已映射成员时，系统必须同步姓名、部门、职位、手机号及启用状态，同时保留管理员维护的角色。
4. 当企微成员标记为部门负责人时，系统必须在成员写入后更新对应部门主管；负责人缺失或冲突时必须记录逐项失败。
5. 当后续快照中缺少已映射成员时，系统必须禁用该成员、清理部门主管/直属上级引用，并保留业务负责人和审批历史。
6. 本地手工成员没有企微映射时，同步不得删除或禁用该成员。

### R6：批次、并发与原子性

1. 同一租户和平台同时只能存在一个 `FETCHING` 或 `APPLYING` 批次。
2. 当用户重复应用同一批次时，系统必须拒绝或幂等返回原结果，不得重复创建部门、成员或映射。
3. 部门树和成员/映射写入必须在单一数据库事务中执行；不可恢复错误时整批回滚。
4. 批次必须记录创建人、应用人、状态、计数、开始/结束时间和安全错误摘要。
5. 成功应用后，系统必须更新集成的最近同步状态、写操作日志，并向操作人发送站内通知。

### R7：页面闭环

1. 企业设置的企微卡片必须允许已验证管理员开启或关闭“同步组织架构”。
2. 组织架构页面必须提供“企业微信同步”入口，并显示未配置、未验证、未开启、正在预览/应用等禁用原因。
3. 从组织架构页面打开同步时，必须默认使用左侧树当前选中部门作为同步承载父级；未选择时使用本地组织根部门，并在生成预览前明确显示目标部门与新增/更新语义。
3. 同步抽屉必须展示最近批次、差异统计、冲突列表和风险说明，并支持创建预览、提交冲突解决方案和应用。
4. 当批次状态变化时，页面必须刷新状态；成功应用后必须刷新部门树和成员列表。
5. 无 `system:dept:sync` 权限的用户不得看到同步执行入口，但仍按原权限读取组织架构。

### R8：安全、租户与日志

1. 所有配置、批次、差异、映射、部门和成员查询必须限定当前租户。
2. Secret 和 access token 不得写入批次、差异、操作日志、错误信息或浏览器响应。
3. 企微返回内容必须按白名单规范化，原始响应不得整体持久化。
4. 启停同步、创建预览、提交冲突方案和应用批次必须写操作日志。

## 6. 非目标

- W3.2 不实现企微扫码/OAuth 登录、外部身份登录绑定或解绑；这些属于 DB-014 / W3.3。
- W3.2 不实现企微消息发送、消息渠道开关或重试任务；这些属于 DB-006 / W3.3。
- W3.2 不实现钉钉、飞书组织同步，但数据模型和枚举应保持 provider 可扩展。
- W3.2 不构建定时自动同步；先完成管理员手工预览与应用闭环。

## 7. 完成标准

- 数据迁移、外部映射、批次/差异模型、NestJS API、权限、审计和 Vue 页面全部完成。
- 自动化覆盖首次预览、映射优先、冲突、后续更新、成员缺失禁用、租户隔离、并发和回滚。
- 本地 PostgreSQL 迁移、typecheck、lint、build、规则测试、Smoke 和浏览器验收全部通过。
- DB-013 只有在上述条件全部满足后才能标记 `VERIFIED`；W3.3 缺口继续保留。
