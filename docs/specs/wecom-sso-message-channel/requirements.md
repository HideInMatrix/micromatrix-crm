# W3.3 企业微信统一登录与消息渠道需求

## 1. 目标

在 W3.1 企业微信安全配置和 W3.2 组织同步、外部成员映射基础上，对齐 Cordys 的企业微信扫码/OAuth 登录与企业微信应用消息通知。W3.3 必须形成“登录入口 → 一次性 state → 外部成员识别 → 本地账号会话 → 登录审计”和“事件开关 → 接收人映射 → 投递任务 → 失败重试 → 投递审计”的完整闭环。

## 2. Cordys 源码事实

- PC 登录页仅在当前组织同步平台已启用时展示二维码入口，使用 `corpId`、`agentId`、回调地址和后端签发的 `qr-wecom` state；企业微信工作台通过 `wxwork` 环境判断进入独立网页 OAuth，使用 `snsapi_privateinfo`、`agentid` 和 `wecom` state。
- `OAuthStateService` 使用 256 位安全随机数、10 分钟 TTL、流程前缀、服务端保存和一次性消费，拒绝缺失、跨流程、过期与重放 state。
- `SSOController/SSOService` 先交换 access token，再调用 `/auth/getuserinfo` 获取 `userid`，只允许已同步且启用的本地成员登录，不自动创建未知成员。
- 企业微信登录复用本地会话签发逻辑并写登录地址；OAuth 登录可补充成员资料，普通二维码登录不覆盖组织同步数据。
- `MessageTask` 为每个事件分别保存系统、邮件、企微、钉钉和飞书渠道开关；消息设置页面仅在平台配置启用时展示对应第三方渠道列。
- `NoticeSendService` 按事件有效设置分发到不同 sender；`WeComNoticeSender` 只向已同步的外部 userId 发送文本消息，并复用同一企微配置和 token 获取逻辑。
- Cordys 发送器吞掉第三方异常且没有持久化投递重试明细。MicroMatrix 按既定 W3.3 完成标准补充可查询的投递任务、有限重试和结果审计。

## 3. 多租户适配

- 企业专属入口可通过 `/login?tenant=<slug>` 固定企业；通用登录入口优先使用部署变量 `WECOM_DEFAULT_TENANT_SLUG`，未配置时仅在系统能解析唯一可用企微企业时直接登录。PC 点击企微图标不得要求用户手工输入企业标识；多企业且无默认值时必须提示配置专属入口或默认企业。
- OAuth state 必须绑定租户、集成、浏览器随机 cookie、流程和受限站内返回路径；原始 state 与 cookie nonce 不得明文持久化。
- W3.2 `ExternalUserMapping` 是企微成员与本地成员的唯一组织映射来源；W3.3 `ExternalIdentity` 只记录登录身份状态和审计，不复制组织字段。
- 未同步成员、停用成员、停用企业、已解绑身份或关闭同步平台均不得通过企微登录。

## 4. 验收需求

### R1：登录入口与配置门槛

1. 当企业微信配置已验证且组织同步开关已开启时，系统必须为该企业公开统一登录配置和授权入口。
2. 当 URL/部署默认企业不存在，或平台未配置、未验证、未开启时，系统必须隐藏或拒绝企微登录并返回不泄露配置细节的错误。
3. 登录页必须保留现有邮箱密码登录，并提供与 Cordys 一致的“其他登录方式”切换入口。
4. 授权回调地址必须由服务端配置或同源地址生成，不得接受任意外部重定向地址。

### R2：OAuth state 安全

1. 当发起企微登录时，系统必须生成至少 256 位随机 state，保存其 SHA-256 摘要，并设置 10 分钟有效期。
2. state 必须绑定租户、企微集成、Cordys PC `QR_WECOM/qr-wecom` 或工作台 `WECOM/wecom` 流程、各自独立的浏览器随机 HttpOnly cookie 和受限站内返回路径。
3. 当回调发生时，系统必须原子校验并一次性消费 state；缺失、过期、浏览器不匹配、流程不匹配和重放均必须拒绝。
4. 原始 state、cookie nonce、应用 Secret 和 access token 不得进入数据库日志、操作日志或错误响应。

### R3：身份识别、绑定与解绑

1. 当企微返回 userid 时，系统必须按当前租户/provider 查询有效 `ExternalUserMapping`，不得按姓名、邮箱或手机号猜测账号。
2. 首次成功登录必须创建 ACTIVE 外部身份；后续登录必须复用同一身份并更新最近登录时间。
3. 同一企微 userid 只能绑定一个本地成员，同一成员同一平台只能有一个活动身份；冲突必须拒绝并审计。
4. 管理员必须可以查看成员的企微身份、按现有成员映射绑定或恢复身份，以及安全解绑。
5. 当成员禁用密码登录且解绑会移除最后可用登录方式时，系统必须拒绝解绑，避免账号锁死。
6. 已解绑身份不得在下次回调中被静默重新激活；必须由管理员显式恢复。

### R4：会话与登录审计

1. 成功识别 ACTIVE 成员后，系统必须复用现有 JWT access/refresh token 和 `CurrentUser` 返回结构。
2. 外部登录不检查 `passwordLoginEnabled`，但必须检查成员和租户状态；密码登录原行为不得回退。
3. 每次企微登录成功或失败必须写 `LoginLog`，记录租户、成员（可识别时）、`WECOM` 或 `WECOM_OAUTH2` 认证类型、外部主体摘要、IP、User-Agent 和安全错误信息。
4. OAuth 回调失败不得产生 JWT，不得留下可重复使用的 state。

### R5：企微消息渠道设置

1. `MessageTaskSetting` 必须为 35 个 Cordys 事件增加独立 `weComEnabled` 开关，默认关闭。
2. 消息设置页面仅在企业微信配置已验证且同步平台开启时展示可操作的“企业微信通知”列；否则显示准确门槛说明。
3. 管理员必须可以逐事件和批量启停企微渠道；无 `system:message:update` 权限不得修改。
4. 后端必须再次校验渠道门槛，不能只依赖前端禁用状态。

### R6：投递任务与发送器

1. 当业务事件触发且企微渠道开启时，系统必须为每个有效接收人创建独立投递任务，并保存当次标题、正文、链接和外部 userId 快照。
2. 没有有效外部成员映射的接收人必须留下不可发送的审计结果，不得影响系统站内消息。
3. 发送器必须复用 W3.1 加密凭据和 `WeComClient`，调用 `/message/send` 发送文本消息；浏览器和持久化数据不得获得 Secret/token。
4. 成功投递必须记录 provider message id、发送时间和尝试次数；失败必须记录安全错误码与摘要。
5. 系统消息和企微消息必须相互隔离：任一渠道失败不得回滚业务事务或另一渠道的成功结果。

### R7：重试、并发与投递审计

1. HTTP 429/5xx、超时和企微临时错误必须最多重试 3 次并使用退避时间；永久错误直接进入终态。
2. 多个 worker 同时扫描任务时，同一投递只能被一个 worker 认领；卡在 SENDING 的任务必须可超时恢复。
3. 管理员必须可以分页查看企微投递记录，按状态、事件和关键字筛选，并手工重试失败/终止任务。
4. 手工重试必须校验租户与权限、重置安全状态并写操作日志，不得跨租户操作。

### R8：页面、日志与验证

1. 登录页必须完成企微入口、PC 扫码组件、工作台 WebView OAuth、回调加载、成功登录和明确失败状态；普通用户不得手工输入企业标识。
2. 企业设置必须展示统一登录与企微消息可用状态、登录 URL 和配置前置条件，不新增左侧菜单项。
3. 消息设置必须对齐 Cordys 的第三方列、表头批量开关和单事件开关，并提供投递记录抽屉。
4. 身份绑定/解绑、企微渠道开关、手工重试必须写操作日志；登录尝试必须写登录日志。
5. Prisma 迁移、类型检查、Lint、构建、规则测试、专项 Smoke 和浏览器验收全部通过后，DB-006 与 DB-014 才能标记 `VERIFIED`。

## 5. 非目标与保留缺口

- W3.3 仅实现企业微信；钉钉、飞书登录和消息发送继续保留 provider 扩展位。
- 不实现企微回调事件驱动的增量组织同步、多部门关系、定时组织同步或自动成员创建。
- 不实现邮件 SMTP、公告、租户自定义消息模板和富媒体企微消息；它们继续在暂缓台账中单独跟踪。
- 不覆盖成员已有邮箱或密码，也不允许未知外部成员通过首次登录自动注册；工作台 OAuth 仅在邮箱为空时补全授权邮箱，并可更新手机号、Cordys Boolean 性别和独立用户扩展表中的头像。
