# ADMISSIONS-001 通用招生 CRM 演进边界

> 状态：边界定义 v4（2026-09-24）

## 1. 目标

本主题负责把当前完整 CRM 从“传统销售交易链”逐步演进为可组合的通用招生 CRM。

核心原则不是按某一个客户的页面把系统写死，而是把招生设计中的稳定业务能力抽象成通用能力，再用配置组合出招生场景。

招生场景的目标主链路为：

```text
渠道获客
  → 线索 / 线索池
  → 分配负责人
  → 跟进 / 跟进计划
  → 可配置业务阶段（例如到访、试听、签到）
  → 外部财务系统产生缴费/报名事实
  → 财务系统调用 CRM API
  → 必要时复用既有线索转客户逻辑
  → 更新客户自定义字段
  → 客户 / 联系人沉淀
  → 工作台统计、漏斗、渠道与人员绩效
```

完整 CRM 历史能力已经由 `backup/full-crm-before-admissions-20260924` 分支保留；`master` 只承担后续通用招生 CRM 演进。

## 2. 强制边界

### R1：不得把招生语义写死进基础模型

1. 内部领域仍使用稳定的通用资源语义，例如 Lead/Customer/Contact/Owner/Pool/FollowUp/Stage/ExternalEvent。
2. “学生、招生老师、签到、缴费、渠道”等业务文案必须由模块配置、字段配置、字典、阶段配置或工作台配置表达；业务配置统一收敛到 Lead / Customer 模块配置，不新增招生专用“业务设置”中心。
3. 不创建仅服务某一个客户的 `StudentLead`、`AdmissionsTeacher`、`SignInOnly` 一类硬编码模型。

### R2：先退出产品入口，再删除实现

对客户当前不需要的传统销售模块，按以下顺序处理：

1. 从主导航、快捷入口、搜索和工作台中退出；
2. 清理其它核心页面对它们的强依赖；
3. 确认 API、权限、任务、通知、导入导出、动态表单和数据模型没有剩余调用；
4. 最后才允许删除 Controller/Service/UI/Prisma 模型和 migration 相关代码。

禁止因为“菜单不显示”就立即删除共享底座，也禁止留下已不可达但仍被后台任务调用的半删除模块。

### R3：招生核心底座必须保留

以下能力属于通用招生 CRM 基础设施，不因页面设计稿暂时没有独立入口而删除：

- 登录、组织、成员、角色、RBAC、数据范围；
- 企业集成与 SSO 抽象，企业微信继续作为当前主要入口；
- 动态表单、动态字段、字典、字段校验与表单布局；
- 用户视图、高级筛选、动态列、分页、排序；
- 负责人、负责人历史、资源池、领取、分配、回收、库容、SLA；
- 跟进记录、评论、附件、图片、@成员、跟进计划；
- 导入导出、通知、消息、操作日志；
- Redis、分布式协调、异步任务等运行底座；
- PC / Mobile 双端的共享业务契约。

### R4：联系人不得删除

联系人继续作为独立通用资源保留。

在招生场景中，Customer 可以代表已形成稳定关系的学员/家庭/客户主体，Contact 可以表达家长、监护人、紧急联系人、推荐人或其它关联人员；系统内部不固定这些展示名称。

联系人既可有独立列表入口，也可作为 Customer 的子资源存在。是否在某个招生方案中显示一级入口由模块配置决定，而不是删除 Contact 领域。

### R5：客户公海作为正式业务能力保留

招生业务不仅需要线索池，也需要客户公海承接已转化客户的回收、再分配和重新领取，因此客户公海属于正式产品能力。

- Customer 保留，作为线索转化后的稳定业务主体；
- Customer Pool / 公海保留 PC 与 Mobile 前台入口；
- 保留领取、分配、回收、容量、原因和 SLA 等通用池规则；
- 客户公海继续参与权限、用户视图、搜索和客户列表操作，不进入旧交易链删除范围。

### R6：签到是阶段/业务事件，不是硬编码独立系统

“签到、到访、试听、面谈”等属于可配置业务阶段或阶段事件。

系统必须支持：

- 阶段可配置名称、顺序、启停；
- 阶段变化记录时间、操作者、负责人和来源；
- 工作台和漏斗按配置阶段统计；
- 不同租户可以拥有不同阶段。

不得为了当前客户单独增加固定“签到模块”并让统计直接依赖固定枚举。

### R7：缴费/报名事实属于外部财务系统，CRM 只接收状态同步

缴费、报名成功等交易事实由外部财务系统产生，CRM 不负责生成支付订单、不负责结算，也不因为需要接收缴费结果而继续维护完整的合同、订单、发票、回款链。

CRM 必须提供通用的外部业务事件/API 接入能力，处理规则如下：

1. 财务系统通过受鉴权保护的 API 向 CRM 提交一个可幂等识别的外部事件；
2. 请求由调用方在本次 API 调用中直接传入用于定位资源的查询字段，例如 `studentName=张三`、`phone=13800000000`；系统不得要求调用方预先配置固定的“身份字段组合”；
3. 如果目标已经是 Customer，直接通过现有动态字段服务更新 Customer 的用户自定义字段；
4. 如果目标仍是 Lead，必须调用系统既有的 Lead → Customer 通用转换逻辑，不得在财务回调代码中重新实现一套 Customer 创建、字段复制、负责人处理或关联迁移；
5. 转换成功后，以转换得到的 customerId 写入本次事件要求同步的 Customer 自定义字段；
6. “缴费状态、报名状态、缴费时间、缴费金额”等都不是 CRM 固定字段。是否存在、字段名称、类型、选项和布局全部由用户通过动态表单配置；只有用户实际配置并授权映射的字段才允许被外部同步；
7. CRM 可以保存外部事件处理日志、来源、事件唯一标识、处理状态和必要的审计快照，但该日志不是财务交易模型，也不能演化成第二套账；
8. 同一个外部事件重复通知不得重复创建 Customer、重复转换 Lead 或重复执行转换副作用；
9. 处理失败必须可诊断并可安全重试，不允许出现“Lead 已转 Customer，但本次字段状态未写入且事件被错误标记成功”的半完成状态。

### R7.1：外部 API 使用本次请求的动态字段条件定位唯一资源

外部 API 不预配置“组合身份字段”。调用方在每次请求中自行决定本次使用哪些字段作为查询条件。

例如用户在 Lead / Customer 表单中自行创建：

```text
studentName
phone
status
```

第三方平台可使用自己的 API Key 发起：

```text
where:
  studentName = 张三
  phone = 13800000000

set:
  status = 已缴费
```

系统必须：

1. API Key 继续解析为其创建用户，并继承该用户现有角色、权限和数据范围；
2. `where` 中调用方实际传入的多个字段按 AND 关系精确匹配；
3. 查询字段可以是允许筛选的系统字段，也可以是用户通过动态表单定义的自定义字段；
4. 查询结果为 0 条时返回 `NOT_FOUND`；
5. 查询结果恰好为 1 条时才允许继续更新；
6. 查询结果大于 1 条时返回 `NON_UNIQUE_MATCH`，系统不得自动选择第一条；
7. 调用方遇到 `NON_UNIQUE_MATCH` 时，自行增加更多查询条件，直到当前 API Key 可见范围内只剩一条；
8. `set` 中的更新字段同样可以是用户自定义字段，但必须经过 Metadata / Dynamic Form 的字段存在性、类型、选项、可写性和权限校验；
9. API 不得通过原始 SQL、任意 Prisma where 或其它方式绕过字段白名单与数据范围。

这里的“唯一”是 **本次 API Key 可见范围内，本次查询条件恰好命中一条数据**，不是要求系统事先配置某个固定组合唯一键。

事件幂等与动态条件定位是两个独立边界：

- `organizationId + source + externalEventId` 防止同一外部事件被重复消费；
- 本次请求的 `where` 条件负责定位当前要更新的唯一业务记录。

二者不能相互替代。

### R7.2：线索判重设置只控制入库时的唯一校验范围

当前项目允许不同部门、不同资源池之间彼此不可见，因此同一个真实学生可以被两个相互隔离的招生团队分别跟进。

例如：

```text
部门 A / 线索池 A
张三 + 13800000000

部门 B / 线索池 B
张三 + 13800000000
```

这两条 Lead 在当前业务模型下属于合法并行数据。即使“手机号”字段在表单设计器中开启了 `unique`，也不能因为另一个互不可见线索池已经存在相同手机号而导致当前线索入库失败。

Lead 判重规则不得配置在某一个具体线索池内，而应作为 **Lead 模块级“线索判重设置”**，与“线索表单设置 / 线索池设置 / 线索库容设置”同级。

该模块**不负责重新选择“哪些字段组合判重”**。字段是否唯一仍由“线索表单设置”里的字段配置决定，例如：

```text
手机号
unique = true
```

“线索判重设置”负责定义这类唯一字段在**入库时**按什么隔离范围执行校验。对于当前招生场景：

```text
线索池 A：phone = 13800000000  ✅
线索池 B：phone = 13800000000  ✅

如果 A、B 彼此隔离、互不可见，
则 B 的入库不能被 A 中相同 phone 阻止。
```

因此，现有字段 `unique=true` 不能在线索入库场景中简单解释成“整个 organization 的所有 Lead 全局唯一”；入库校验必须结合目标资源池及其数据隔离范围执行。

具体线索池仍只负责自己的成员、数据范围、领取、分配、回收、隐藏字段等池规则；“线索判重设置”作为更高一级的模块配置，统一规定不同资源池之间的唯一校验隔离原则。

重复校验自身也必须遵守数据隔离边界。A 部门不能因为 B 部门已经存在相同学生而收到“重复线索”的提示，否则唯一校验会成为跨部门数据存在性的侧信道。

“线索判重设置”只服务 CRM 内部的线索新增、导入和进入资源池等入库判重流程。外部财务 API **不读取该设置来决定查询条件**。

财务 API 如果使用 `studentName + phone` 后仍然命中多条，则返回 `NON_UNIQUE_MATCH`；第三方平台自行增加部门、校区、报名编号或其它允许查询的字段。CRM 不把“线索判重设置”强加给第三方 API。

因此本阶段**不建立独立的 ConversionResult、Payment、EnrollmentPayment 等固定业务模型**。如某客户需要在 CRM 中展示金额、时间或状态，由其自行定义 Customer 字段并在外部事件映射中选择这些字段。

### R8：首页改造成可配置业务工作台

`/dashboard` 继续作为首页，但首页不再以传统销售商机链为固定事实。

工作台至少支持组合：

- 新增线索；
- 待跟进 / 超时未跟进；
- 阶段转化；
- Customer 自定义业务状态（例如用户配置的缴费/报名状态）；
- 渠道统计；
- 人员绩效；
- 转化漏斗；
- 趋势；
- 快捷创建；
- 我的跟进计划、通知和待办。

统计口径必须来自同一业务事实，点击统计项进入列表时必须带入对应筛选。

### R9：渠道、招生老师、排行榜不创建重复领域

- 招生渠道 → 来源字段 + 字典/渠道配置；
- 招生老师 → Owner/负责人 + 组织成员；
- 排行榜 → 通用指标聚合 + 人员维度；
- 超时未跟进 → SLA + Pool/FollowUp 规则；
- 线索池 → 通用资源池行为；
- 招生漏斗 → 可配置阶段 + Customer 动态字段统计。

这些能力不得分别建立一套招生专用用户、渠道、回收、排行模型。

## 4. 页面与信息架构边界

第一阶段目标主导航建议只围绕：

```text
首页
线索
客户
仪表板/分析（后续按工作台与分析边界决定名称）
系统
```

其中：

- “线索”内部包含普通线索与线索池；
- “客户”内部包含客户、联系人、客户公海；
- “自定义表单”不再必须作为一线业务人员一级导航，可迁入系统配置；
- 传统销售交易链不再出现在主导航、全局搜索和首页快捷创建中。

## 5. 数据删除边界

本阶段只定义删除候选，不立即做破坏性数据库迁移。

任何模型物理删除前必须满足：

1. Web 与 Mobile 无路由/组件引用；
2. API Module 无 Controller/Service 引用；
3. Home、Search、Notification、Approval、Import/Export 无引用；
4. Prisma relation 已解耦；
5. Seed、规则测试、Smoke、Browser 测试不再依赖；
6. 目标通用能力已迁移；
7. 空库 migration + Seed + 全量测试通过。

## 6. 明确非目标

- 不复制客户原型中的固定文案和固定状态枚举；
- 不在本阶段重写完整财务、教务、排课、考勤系统；
- 不把“缴费”扩展为完整财务 ERP；
- 不创建独立 ConversionResult/Payment 模型来复制财务系统事实；
- 不把“缴费状态/报名状态/缴费金额”等固化为 Customer 系统字段；
- 不允许外部财务 API 绕过既有 Lead → Customer 转换服务直接插入 Customer；
- 不为了减少菜单数量破坏动态表单、RBAC、资源池、跟进等共享底座；
- 不在删除交易链时同步删除 Contact；
- 不以隐藏菜单作为物理删除完成的证明。
