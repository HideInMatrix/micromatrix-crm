# 开发约定

## 项目身份

- 当前项目名称为 **招生CRM**，Git 仓库名为 `micromatrix-crm`。
- 不得将其他项目的品牌名称移用到本项目，也不得擅自改变项目名称。

## 1. 产品边界

- 当前产品边界以 `docs/specs/`、现有代码、Prisma contract 和自动化测试为准。
- 不因历史代码、数据库残留或旧页面目录存在某个模块，就将其视为当前启用的产品能力。
- 联系人不是独立业务资源；家长姓名、电话等信息属于线索/客户表单字段。
- 审批能力保留，但当前不参与招生主流程自动触发；不得成为线索、客户、跟进或外部事件的默认前置环节。
- 商机、产品、报价、合同、回款、发票、订单、标讯等传统销售交易链不属于当前产品范围；重新引入前必须明确新的产品需求与数据边界。

## 2. 文档维护

- 当前文档入口是 `docs/README.md`；产品边界见 `docs/specs/admissions-crm-transformation/requirements.md`。
- 已删除或停用的能力必须同步清理当前产品入口、权限、API 契约、测试和文档引用；仅用于兼容旧链接的重定向应明确标记。
- 整份文档如果已与当前架构相反，直接重写或删除并更新引用；不要只加“已废弃”标题继续污染全文检索。
- 已完成专项不长期保留独立任务清单；把仍有维护价值的约束合并进稳定领域 `requirements/design`，实施过程与历史验收通过 Git 追溯。
- 需要历史实现、旧测试数量或旧迁移过程时优先使用 Git 历史，不新增长期过程日志。
- 开始修改前，先阅读文档索引、本约定、对应领域规格和专项文档，并检查当前代码、测试及 Git 工作区；不能只根据聊天摘要或旧印象修改。
- 用户已确认的业务规则和当前有效文档是修改边界。重构或修 bug 不得顺手改变已完成的业务行为；确需调整时先明确影响并取得确认。
- 改变业务行为、接口契约、字段映射、权限、回收规则或部署方式时，必须同步更新对应稳定领域文档；文档应记录最终规则、优先级、缺省行为、失败条件和必要示例，而不只记录“做了什么”。
- 完成前核对代码、测试与文档是否一致；提交前检查 diff，确认没有覆盖既有完成项或夹带无关改动。

## 3. 需求交付与自测（强制）

每一项需求、缺陷修复、重构、配置调整和文档修改，都必须由实施者在交付前主动检查并验证实际结果。**修改完成不等于需求完成，类型检查或构建通过也不等于功能验收通过。** 不得把本应由开发者完成的自测转交给用户，也不得在未验证时声称已完成。

### 实施与验证流程

1. **明确验收点**：开始前将用户要求拆成可观察、可验证的结果；检查当前实现、相关测试、文档和 Git 工作区，保留与本次任务无关的已有修改。
2. **实现后先自查**：检查完整 diff、调用链、异常分支、权限和数据范围；确认没有遗漏关联端、接口、配置、导航、日志或文档。新增/修改的业务行为应补充或更新自动化回归测试。
3. **按影响范围执行验证**：使用仓库实际存在的脚本、测试工具和本地环境，不虚构不存在的命令；至少执行与本次变更直接相关的测试。必要时继续执行类型检查、Lint、构建、迁移校验和端到端测试。
4. **验证真实运行结果**：不能只阅读代码或依赖静态检查。启动本地服务，通过实际页面、接口或业务流程操作，确认数据变化、交互结果、权限限制和错误提示符合验收点。
5. **修复并复测**：任何检查或测试失败，都要先定位并修复；修复后重新执行受影响的检查和回归验证，不能用一次失败后的旧结果作为最终结论。
6. **交付前复核**：再次检查 diff、工作区和测试结果，确认没有引入无关修改；向用户说明实际执行的检查/测试、结果，以及尚未验证的部分和具体原因。

### 按变更类型验收

- **PC / Mobile UI**：必须启动本地应用并在浏览器中检查真实页面。PC 检查目标分辨率下的布局、样式、交互、数据状态和控制台/网络错误；Mobile 使用移动视口或设备工具栏检查布局、弹窗、滚动、输入和触控交互。涉及企业微信容器差异时，能访问真实容器就做真实验证；无法访问时必须明确标注该项未验证，不能用普通浏览器结果代替。
- **API / 业务逻辑**：执行相关单元或集成测试，并实际调用本地接口验证成功、失败、边界和重复请求场景。涉及租户隔离、角色权限或数据范围时，至少验证允许和拒绝两侧；涉及事务、幂等、导入导出或外部事件时，验证对应的数据结果和审计结果。
- **业务闭环**：按用户描述的真实流程准备本地测试数据，覆盖涉及的 PC、Mobile、接口、跟进记录/计划、负责人、线索池/客户公海及通知等环节；验证正向流程和关键异常分支。不得只验证单个按钮或单个接口就宣称闭环通过。测试数据仅在本地/测试环境创建；是否保留或清理按用户要求执行，不得擅自删除用户要求保留的数据。
- **数据库 / Migration**：校验 Prisma contract、生成产物和 migration graph；在本地开发库验证迁移前后结构及关键读写。破坏性迁移还必须执行正式环境只读 precheck；未经明确授权不得在生产环境执行破坏性验证。
- **文档 / 配置**：检查内容与当前代码、接口和实际配置一致；执行格式检查、相对链接检查和关键术语/过时信息检索，并重新阅读修改后的完整段落。文档任务不需要无意义地启动业务服务，但必须验证文档自身及其引用。

### 验收与汇报要求

- 测试范围应与风险匹配；改动影响 PC 和 Mobile 时不能只检查其中一端，影响共享逻辑时不能只检查单个调用方。
- 自动化测试通过不能替代 UI 视觉检查或真实业务闭环；本地页面可用也不能替代接口权限和数据一致性验证。
- 环境、账号、第三方容器或服务不可用时，应完成可执行的本地验证，并逐项列明阻塞项；不得把“未运行”“未观察”描述成“通过”。
- 最终交付说明必须区分**已执行且通过、已执行但失败、受环境限制未执行**，必要时附上关键命令、页面/流程和测试数据说明。没有实际执行的测试不得写成已通过。

## 4. 工程工具链

- Node.js：`>=25 <26`；pnpm：`11.25.0`，使用 workspace。
- TypeScript：`7.0.2`。
- PC：`apps/web`，Vue 3 + Vite + Element Plus。
- Mobile：`apps/mobile`，Vue 3 + Vite + Vant 4 + UnoCSS presetWind4。
- `packages/shared` 只放 API/前端都能消费的纯 TypeScript 类型、枚举、权限和领域逻辑，不引入 DOM/Vue/Axios。
- `packages/frontend-shared` 放 PC/Mobile 共用的浏览器 HTTP、Token、设备判断等能力。
- 提交前按改动范围执行 typecheck、tests、build、ESLint 和 `git diff --check`。

## 5. Prisma ORM 8

- 数据模型唯一事实源：`apps/api/src/prisma/contract.prisma`。
- `prisma contract emit` 产物位于 `apps/api/src/prisma/contract.json` 与 `contract.d.ts`。
- 生产运行时唯一 client 创建点：`apps/api/src/prisma/db.ts`。
- `apps/api/src/prisma.service.ts` 只做 NestJS DI / lifecycle wrapper，不自行创建 client。
- 正式 migration graph：`apps/api/migrations/`；结构变化只新增 forward migration。
- 禁止重新引入 Prisma 7 `schema.prisma`、Prisma Client class、`extends PrismaClient`、生产 client factory、`src/prisma/generated/` 或 `db push` 工作流。
- 详细规则见 [Prisma ORM 8 Migration 规范](./prisma-migration-policy.md)。

## 6. NestJS 后端

- 业务模块放在 `apps/api/src/modules/<domain>/`；跨域基础能力放在 `src/common`、`src/prisma` 等明确公共边界。
- 除显式 `@Public` 外统一经过 AuthGuard；功能权限使用 canonical 权限码，写操作保留审计。
- 所有业务查询必须保持 tenant 隔离；列表、详情、更新、删除同时应用目标权限对应的数据范围。
- 多角色数据范围只能合并真正拥有目标权限的角色，不能用无关角色扩大数据边界。
- 业务异常使用明确的 NestJS HTTP exception；对外错误不得泄露数据库、Secret 或内部堆栈。
- Redis 是缓存、Pub/Sub、协调和 BullMQ transport，不是业务真相源；业务状态和幂等状态存 PostgreSQL。

## 7. 元数据与动态表单

- 模块表单、字段定义、Field/Blob 值、显隐/联动、唯一性和附件生命周期统一复用 Metadata 能力。
- 固定业务列承担 tenant、owner、pool、模块明确存在的状态、索引和资源关联；线索不再具有固定系统阶段/状态字段。
- 跨模块字段复制只能使用显式 formLink；禁止靠字段同名、`cf_` 前缀或运行时猜测自动复制。
- 新字段必须考虑 PC/Mobile 可见性、列表展示、筛选能力、唯一性范围和导入导出语义。

## 8. PC 前端

- 路由 View 主要负责页面编排；稳定业务区域拆成组件，加载/筛选/表单状态优先抽到 composable。
- API 调用统一进入 `src/api/` 或共享前端 API 层，不在多个 View 重复 HTTP 协议。
- PC 使用 Element Plus；模块配置和页面入口只展示真实存在的路由与业务能力。
- 普通布局、间距和响应式优先使用现有 utility / design token；不要为简单布局新增大量一次性 CSS。
- UI 实现以当前产品设计稿、现有组件和项目级样式 Token 为准。

## 9. Mobile 前端

- `apps/mobile` 是独立应用，不把 Mobile 页面塞回 `apps/web`。
- 使用 Vant 4 + UnoCSS presetWind4；选择、Popup、Dialog、Tabbar 等优先使用 Vant 原生组件。
- 一级页面使用 Mobile Tabbar；详情/新建/编辑等深层页面按当前路由规则隐藏 Tabbar。
- 企业微信容器中的重复 Header、返回按钮等由统一环境判断控制，不能在每个页面复制 UA 判断。
- Mobile 搜索、二级选择和动态表单复用共享协议，不硬编码字段。

## 10. 新业务能力接入

新增业务能力前先确认：是否属于招生CRM项目边界、是否已有可复用的元数据/权限/池/跟进能力、是否会引入新的数据库结构。

新的持久化业务资源通常需要同步考虑：

1. Prisma 8 contract + forward migration。
2. shared DTO / enum / 权限码。
3. tenant / owner / department / DataScope。
4. Metadata 表单字段和动态值边界。
5. NestJS module / controller / service / DTO。
6. PC 与 Mobile 的入口和交互。
7. 导入导出、通知、日志、外部 API 是否需要接入。
8. 数据库迁移检查、权限/数据范围验收与 UI 验证。

如果能力只服务线索或客户配置，应优先进入现有模块配置，不另建没有独立业务意义的设置模块。

## 11. 完成标准

- 代码、路由、导航、权限、数据库 contract 和文档必须描述同一产品边界。
- 类型检查与构建通过不代表真实客户端验收可以省略；企业微信等 Provider 容器行为仍需要真实客户端验证。
- 对 destructive migration，开发库验证不能替代正式环境发布前的只读 precheck。
- 不提交与当前任务无关的历史工作区修改，也不通过回滚覆盖已有未提交工作。
